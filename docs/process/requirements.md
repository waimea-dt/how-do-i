# Requirements Specification

Before you build anything, you need to know exactly what you're building - and why. That's what a requirements specification is for.

## What Is a Requirements Specification?

A requirements specification is a document that **clearly describes what a system or product must do**. It's written **before any design or development begins**, and it acts as the agreed reference point for everyone involved in the project.

It answers three core questions:

- **What** does the system need to do?
- **Who** is it for?
- **What constraints** must it work within?

## Why Is It Essential?

Without a requirements specification, projects go wrong - often in predictable ways:

- Developers build the wrong thing because the brief was unclear
- Time and effort is wasted going back and reworking decisions
- Clients or end users are disappointed because their expectations weren't captured
- Features get added late, blowing out the budget and timeline

A good req spec prevents all of this by making expectations explicit and agreed upon from the start.

## What Goes in a Requirements Specification?

A typical req spec includes:

- **Purpose** - what problem is being solved, and for whom
- **Stakeholders** - who will use the system, and who has an interest in it
- **Functional requirements** - a list of specific things the system must do
- **Relevant implications** - social, ethical, legal, and other real-world considerations

## Requirements Must Be Testable

A well-written requirement should be specific enough to test. Vague requirements cause problems:

| Vague | Specific and testable |
|---|---|
| "The app should be fast" | "Search results must appear within 1 second" |
| "It should be easy to use" | "A new user must be able to complete registration in under 3 minutes without help" |
| "It needs to be secure" | "Passwords must be at least 8 characters and stored using hashing" |

If you can't write a test for a requirement, it's not specific enough yet.
